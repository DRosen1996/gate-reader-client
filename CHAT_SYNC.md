# Chat-triggered sync adapter (not deployed)

The optional `python3 -m review.sync_service` process listens only on loopback port8788. It is separate from the read-only reader. No timer, queue, progress page, task database or status endpoint is added. Schema remains2. The fixed database is `/review-data/ledger.sqlite`; the fixed history start is September1,2026 Beijing time. The existing Client fixes its upstream to HTTPS gate-reader.gatelens.site and performs Gate GETs only.

POST `/review-sync` accepts only JSON `{"request_id":"canonical-lowercase-uuid"}` (maximum128bytes). It requires a protected REVIEW_SYNC_TOKEN distinct from READER_TOKEN. No command/path/SQL/environment/date is accepted. Duplicate headers/JSON keys, browser Origin, extra parameters and other methods are rejected. At most8 connection threads and one nonblocking writer are admitted; contention returns409, never enqueues.

Under the same flock: verified backup → existing CLI sync with fixed acceptance-time end → existing CLI check → full logical revision → atomic success marker. Backups are private, never overwritten, with checksum receipts; retained until a separately approved retention policy exists. Original JSON remains append-only. Initialization, ingestion, sync, notes, backup and restore share the same lock. CLI children inherit the verified same-inode owner-only lock FD; they do not receive the sync credential. Reader mount remains read-only. Manual writes must use these locked project entrypoints; arbitrary external SQLite writers are outside this advisory-lock protocol.

Only a successful job atomically replaces ledger.sqlite.last_verified_sync.json (0600 plus file/directory fsync). It contains request_id, cutoff, checked_at and a logical revision. Existing review-summary exposes last_verified_sync plus matches_current_ledger. Every fact table participates in the revision; later writes/restore/corruption invalidate current-match. Schema is not expanded. Missing/invalid markers are not successes.

The explicit client API is `review.sync_client.trigger(request_id, timeout=180)`; it uses only fixed HTTPS POST and the separate protected sync secret. No automatic retry or fallback writes occur. A lost/failed response raises SyncUnconfirmed. Then use the existing read Client to fetch review-summary and call `verified_in_summary(request_id, summary)`. Only the exact ID, matching current revision and sufficient cutoff confirm completion. Old markers and newer cutoffs alone do not prove this request succeeded.

Disconnect does not cancel the accepted action; response-write errors do not reverse successful completion. A failure can leave committed pages, retained backups and an older marker; do not automatically restore or resend. An explicit new user intent uses a new UUID and existing source-ID deduplication. An unchanged successfully verified UUID returns the previous result without another backup/sync. A failed UUID with an existing backup is deliberately not implicitly resumed; inspect evidence and explicitly authorize a new attempt. Process termination may interrupt the task: no success is claimed without the marker. Partial ranges remain resumable through existing synchronization logic.

## Separate deployment approval

No real credential is created/configured by this change. An operator must approve/configure an isolated non-root worker with write access limited to the dedicated ledger/backup directory, protected separate sync/read credentials, same-domain exact-route reverse proxy, and retained read-only reader access. Never grant the reader a writable mount, shell/exec API, Docker socket or arbitrary command capability. For the current loopback-only worker, use a host process with OS filesystem sandboxing and no privileges/capabilities; proxy localhost8788. Do not publish the bind on a public interface. Only the operator, not HTTP requests, configures execution environment.

The reader image must contain readonly.py, ledger.py, write_lock.py and verified_sync.py alongside the existing package initializer; fresh-install helper now copies these dependencies. An existing deployed reader needs a separately approved code/image update to expose the marker; the worker alone does not make the old summary aware of it. This PR does not run the installer or alter existing deployment overrides.

Measure production synchronization duration and proxy/client timeouts during deployment acceptance. CLI20s timeout is per upstream request, not an entire sync deadline. Configure header/body deadlines and rate limits at the proxy; the worker bounds connections.180s client timeout is configurable by the trusted caller, not a guarantee that production finishes in180s. A timeout remains unconfirmed; do not retry automatically. Concurrent read-only DELETE-mode SQLite reads can transiently contend with writes; retry GET safely, without reissuing POST.

Acceptance: synthetic auth separation, strict inputs, inherited/process/thread locking, duplicate success, backup/check failure and partial commits, disconnected clients, old/stale markers, current logical revisions, no auto retry, existing Gate routes and browser replay. Separately on server: backup recoverability, no data-dir permission changes, actual fixed target, proxy timeout behavior and exact-marker readback. Full-history boundary semantics remain provisional.

Rollback: remove the exact POST proxy route and stop the worker, revoke only sync capability, retain ledger/backups/marker and lock files. Do not restore an old database merely to roll back code. Keep read services on compatible code; old CLI versions lack the coordinated writer lock and must not run alongside the worker. No production merge/deploy performed.

## Operator deployment helper

`tools/deploy_chat_sync.py` provides separate `prepare`, `activate`, and `rollback` actions. Invoke from an archive of the approved commit, with a local checkout containing that Git object. Preparation checks every tracked source file against the commit, the existing reader-only Compose layout, its isolated old-installer build context, expected image/UID/read-only mount, private data permissions, port availability and nginx structure. It refuses unsupported server directives, aliases, ambiguous TLS servers, cleartext/mixed listeners or existing sync routes. The nginx lexer preserves comments, quotes and all original bytes; only one exact location is inserted in the exclusively TLS443 target server.

Preparation retains original configuration privately, tags the old image, builds a separate code-only reader image, then locally generates a distinct sync credential. It captures the existing container environment in memory, retains only READER_TOKEN and writes only those two tokens to root-owned0600 `/etc/gate-review-sync.env`; it never prints values or copies Gate API keys to the worker. No credentials enter build context. The caller must have approved sudo access; do not run the Python helper itself as root. Credentials for a remote chat environment must be transferred separately by the user through a protected channel.

Activation rechecks source, prepared-artifact hashes, credentials/permissions, image tag, running old reader, free worker port and unchanged configuration. It recreates only `reader` with `--no-deps --no-build`, preserving its read-only mount, checks marker-aware summary without displaying account data, installs the sandboxed systemd service and verifies a GET rejection, then runs nginx syntax validation before reload. Service is persistent across reboot, with Restart=no; no timer, collection schedule or production POST is created. The worker can only write the private data bind in its mount namespace. The client/body timeout is5s and upstream response timeout1800s; actual production duration remains unmeasured.

Rollback verifies retained configuration and refuses external drift. It attempts service stop, nginx restoration and reader restoration separately; a failed stop does not skip the other restorations. It pins the retained old image explicitly. On successful stop it removes only this helper's unit and credential file. Partial failure is reported with ROLLBACK_INCOMPLETE and private state retained. Original old-installer recovery files, data, backups and other Compose stacks are never removed. Preparation/build failures do not switch running services. Failed preparation must be inspected privately; no automatic retry. No server deployment has been executed by this repository validation.
